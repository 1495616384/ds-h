## 1. 定位与不可推迟的原因

评测体系是本项目的验收对象。若不先定义判定规则：

- Report IR 的 Diff 设计（`04_REPORT_IR.md` §44）没有验收对象；
- Accuracy Validator 无法确定「什么算一致」；
- 更换模型 / 模板 / 实现后没有任何可比依据。

因此本文档与 IR Schema 属于同一批先行交付物（开发顺序 M0）。

---

## 2. 三类「标准答案」必须分离

历史报告中混杂着三种性质完全不同的信息。V1 把它们混为一谈，导致数据泄漏与循环验证。v0.2 明确分离：

| 类别 | 内容 | 允许来源 | 用途 |
| ---- | ---- | ---- | ---- |
| **G1 输入侧数据** | 原始检测数据、文字资料、图片、模板 | 仅来自历史项目的原始档案 | 作为系统输入 |
| **G2 事实清单** | 这份报告应当涉及哪些事实项 | 可从历史报告正文提取 | 覆盖度检查 |
| **G3 事实值 Ground Truth** | 每个事实的值 | **必须从 G1 独立推导**（人工计算 / 确认），**禁止抄录报告正文** | P0 数值比对 |
| **G4 报告形态** | 章节结构、表格数量、结论方向、版式 | 历史报告正文 | P1 / P2 / P3 比对 |

核心规则：

> **历史报告正文可以告诉系统「应该有哪些事实」，但不能告诉系统「这个事实的值是多少」。**

这条规则是堵住数据泄漏的关键。若 G3 抄自报告正文，则系统测的是「复述能力」，不是「从原始资料生成报告的能力」。

G4 的来源限制（V2.1-7）：

> silver 用例的结论方向必须从 G1（原始输入数据）+ 已确认的 Criterion 推导得到；若某用例的结论方向只能从历史报告正文读出，则该用例的结论方向维度降级为 bronze，**不得作为 P0 的结论方向依据**。

理由：silver 用例的结论方向（G4）若在人工「确认」时参照了历史报告正文，就是**在抄报告**——恰好是本节明令禁止的泄漏路径，只是从数值泄漏换成了判定泄漏。

## 3. 防泄漏与防循环验证

### 3.1 链路分离

```text
逆向链路（构建期，只跑一次）
  历史报告 → 逆向抽取 → 人工确认 → 冻结为 JSON 固件

生成链路（评测期，可反复跑）
  JSON 固件 → 系统 → 报告 → 比对
```

- 逆向链路使用的模型 / Prompt 配置与生成链路**独立登记**，允许不同模型；
- 逆向产物一经人工确认即**冻结**，生成系统不参与、不回写；
- 评测运行时，生成系统**只读固件**，不调用任何逆向 Skill。

### 3.2 已知错误登记（known_issues）

历史报告中的数值笔误、结论错误必须显式登记，比对时排除：

```json
{
  "known_issues": [
    {
      "fact_id": "fact:component.K003.concrete_strength",
      "original_value": 32.4,
      "correct_value": 23.4,
      "reason": "报告正文笔误，原始检测记录为 23.4",
      "confirmed_by": "...",
      "confirmed_at": "..."
    }
  ]
}
```

**若不登记 known_issues，系统「正确地纠正错误」会被判为不一致，评测体系将反向激励团队复制历史错误。**

### 3.3 白名单登记制（v0.2 新增）

白名单是数字锚定（§6.4）的**唯一例外通道**，因此必须治理，不得由 AI 现场决定（与 `04_REPORT_IR.md` §41.2 R2 一致）。

登记表随评测 Schema 冻结，条目结构：

| 字段 | 说明 |
| ---- | ---- |
| `pattern` | **模式级登记**（正则 / 类别），不接受逐条具体数字 |
| `reason` | 为何该模式不属于事实数字（如章节号、条款号、页码） |
| `scope` | 生效范围（Section / Template / 全局） |
| `confirmed_by` | 确认人 |

规则：

1. **确认方必须与生成侧分离**：白名单由评审方确认，被评测的团队不得自行增补；
2. 新增条目必须在评测报告中可见（不得静默扩表）；
3. 之所以不接受「逐条数字登记」：条目数会随报告量线性膨胀，白名单最终退化为形式，红线失效。

## 4. Evaluation Case 分级

不允许以「原始输入必须齐全」作为入集门槛——那会使评测集规模被外部档案现状卡死。改为分级承担：

| 级别 | 条件 | 可测指标 | 数量预期 |
| ---- | ---- | ---- | ---- |
| **gold** | G1 + G3 + G4 齐全 | P0 数值 / P1 结构 / P2 文本 / P3 版式 | 少 |
| **silver** | 有部分 G1（如仅 Excel），G3 可从该部分推导 | P0（部分字段）/ P1 结构 / P2 结论方向 | 中 |
| **bronze** | 仅有报告（G2 + G4） | P1 结构 / P2 语言风格 / P3 版式 | 多 |

分级的使用规则：

1. 门禁阈值只由 gold 用例承担（见 §7）；
2. silver / bronze 用于趋势监控与广覆盖，不单独触发构建失败；
3. 每份用例必须在 `meta.json` 中声明级别，级别不得事后提升。

## 5. Evaluation Case 数据结构

```text
cases/<case_id>/
├── meta.json            # 用例标识 / 级别 / 类型 / 来源 / 陷阱标注
├── inputs/              # G1 输入侧数据（原始检测数据、文字资料、图片、模板）
├── ground_truth/
│   ├── facts.json       # G3 事实值（独立推导）
│   ├── fact_list.json   # G2 事实清单
│   ├── structure.json   # G4 章节路径 / 表格数 / 图数 / 表格列头
│   └── conclusion.json  # G4 结论方向（枚举）
├── known_issues.json
└── expected_issues.json # 本用例预期必须被系统发现的 Issue（用于「正确失败」评测）
```

### 5.1 meta.json

```json
{
  "case_id": "case-001",
  "case_level": "gold",
  "report_type": "...",
  "traps": ["missing_data", "unit_anomaly"],
  "source_project": "...",
  "created_at": "..."
}
```

### 5.2 expected_issues.json —「正确地失败」的验收对象

这是本系统区别于普通文档生成器的关键评测项。系统在最该报错的地方没报错，是最严重的缺陷类型。

```json
{
  "expected_issues": [
    {
      "rule_id": "FACT.MISSING",
      "fact_id": "fact:building.design_grade",
      "severity": "error",
      "note": "该用例刻意移除设计强度等级，系统必须报 missing 而非补全"
    }
  ]
}
```

评测规则：**expected_issues 中的每一项都必须出现在系统输出的 IssueList 中**，否则该用例判定为失败（无论其他指标多高）。

## 6. 判定规则

### 6.1 数值一致性（P0）

工程报告的数值比对**按显示精度**进行，不按浮点相等。

```text
compare(a, b, scale):
    round(a, scale) == round(b, scale)
```

| 情形 | 规则 |
| ---- | ---- |
| 直接来自输入的值 | 以 G3 的原始单位与原始精度为准，按显示精度四舍五入后必须相等 |
| 派生量（均值 / 统计量） | 先以相对误差 ≤ 1e-9 判定计算正确性，再按显示精度比对 |
| 单位 | 必须与 G3 一致；单位不一致即为 error |
| 量纲 | quantity_kind 必须一致；不一致即为 error（即使数值巧合相等） |

**不使用「容差百分比」作为默认策略**——数值错误在工程报告中不可用容差掩盖。确需容差的场景（如不同仪器的重复测量）必须逐项显式声明。

### 6.2 表内自洽（P0）

合计 = 分项之和；最大值 ≥ 均值 ≥ 最小值；计数与明细条数一致。

### 6.3 判定逻辑一致性（P0）

判定结论与限值规则必须一致。例如推定值低于限值却判为「合格」，即为 error。

### 6.4 数字锚定（P0）

数字锚定不是「值是否在全文中存在」，而是**值是否绑定到了正确的 `fact_id`**（与 `04_REPORT_IR.md` §41.2 V2.1-1 一致）。

```text
对每个 token：
    fact_id = 该 token 显式绑定的锚点
    判定：value(token) == fact(fact_id).value   （按显示精度，见 §6.1）
    否则 → error
```

规则：

1. **每个 token 必须显式绑定到 `fact_id`**；评测侧**不设「命中全文 Fact 值集合」这一兜底路径**。值在全文里存在，不等于归属正确：反例——叙述写「构件 K002 强度为 32.4」，实际 K002 = 31.8、K003 = 32.4，token「32.4」虽存在于全文值集合，归属却是错的；
2. 评测比对时，**直接按 anchors 声明的 `fact_id` 与 G3 中对应事实比对**，而不是比对「值本身是否存在于某个集合」。这是让评测独立于生成侧的关键：若由被评测对象自行声明锚点、再以「值存在于全文」放行，等于让被测对象自己给自己发合格证，评测独立性被架空；
3. 锚定范围包含三类载体：**Narrative 段正文**、**Table 的单元格与表标题 / 表注**、**Figure 的图片说明**；
4. 覆盖两类 token：**数值 token** 与**实例标识 token**（构件编号 / 测点编号 / 样品编号 / 文件编号等），实例标识必须绑定到对应事实——例如 `K002` 必须绑定到 `fact:component.K002.id`；
5. 白名单是唯一例外，且只接受**模式级登记**、已由评审方确认的条目（`pattern` / `reason` / `scope` / `confirmed_by`，见 §3.3）；未被登记的 token 一律 error。

未命中即为 error。这是 Narrative 段落的核心防线。

### 6.5 结论方向一致性（P0）

结论以**枚举**比对，不做语义相似度：

```text
qualified / unqualified / level_A / level_B / ...
```

- G4 的结论方向来自人工确认（不由 LLM 判定）；
- 系统输出必须通过程序解析为同一枚举后比对；
- 枚举相等才算一致，措辞不同不影响判定。

### 6.6 结论覆盖度（P0）

结论必须覆盖用例声明的全部检测项。

判定入口（V2.1-7）：结论段必须携带 `covers[]`（覆盖的 Evaluation id 列表）。

```text
覆盖度 = 用例声明的全部检测项，其 Evaluation 至少被 covers[] 引用一次
未覆盖即为 error
```

### 6.7 结构一致性（P1）

比对集合而非文本：

```text
章节路径集合
表格数量与表格列头集合
图片数量
必需要素存在性
```

### 6.8 文本一致性（P2）

**不做全文相似度**。只做：

- 结论要点集合的覆盖比对；
- 术语一致性（受控术语表命中率）。

> 不设「端到端相似度 95%」这类单一指标——它会把 P0 的数值错误掩盖在高文本相似度里。

### 6.9 版式一致性（P3）

基准是**公司标准模板**，不是历史报告。

| 检查项 | 第一阶段 |
| ---- | ---- |
| 章节结构与顺序 | 是 |
| 编号连续性（表 x-x / 图 x-x / 章节号） | 是 |
| 表格 / 图表完整性 | 是 |
| 样式使用合规（实际样式名 vs 模板定义样式名） | 是 |
| 硬编码格式覆盖检出 | 是 |
| 与历史报告逐项版式一致 | **不承诺** |
| 复杂样式继承链判定 | **不承诺** |

## 7. 分层指标与门禁

| 级别 | 指标 | 门禁 |
| ---- | ---- | ---- |
| **P0** | 数值一致率、判定逻辑一致率、结论方向一致率、结论覆盖度、数字锚定通过率、**expected_issues 命中率** | **必须 100%（gold 用例），否则构建失败** |
| P1 | 结构一致率 | ≥ 阈值（由 gold 用例数量与结构约定确定） |
| P2 | 文本覆盖 / 术语一致 | 记录趋势，第一阶段不设硬门禁 |
| P3 | 版式合规率 | 记录趋势，第一阶段不设硬门禁 |

补充规则：

1. gold 用例的 expected_issues 命中率不达 100% 即失败——**「该报错时没报错」是一等缺陷**；
2. 任何 P0 指标下降即视为回归，无论其他指标是否提升；
3. 门禁阈值在 M7 建立基线时**写死进配置**，不得随运行结果调高；
4. **经济门禁（V2.1-7）**：gold 用例数 < 5 时，P0 的 100% 要求降级为「全量报错但不阻断构建」，且评测报告首行必须标注「样本不足，P0 门禁不具统计意义」。

> 经济门禁的原因：gold 用例需要人工从 G1 独立推导全部事实值，是**逐报告的专家工作量**，成本常被严重低估。若 gold 只有 2~3 份，P0 100% 门禁提供的只是**虚假信心**。
>
> 阈值 `< 5` 是**待定的经验值**，需由 §9「任务 0 档案盘点」的实际结果校准。

## 8. 回归流程

```text
确定基线（首次全量跑通）
    ↓
产出 run snapshot，冻结为 baseline
    ↓
任何变更（模型 / Prompt / Skill / 模板 / 程序 / Schema）
    ↓
重新全量运行
    ↓
与 baseline 比对，产出回归报告
    ↓
新增错误 / 已修复 / 未变
    ↓
P0 门禁判定
```

### 8.1 Run Snapshot

```json
{
  "run_id": "...",
  "timestamp": "...",
  "input_hash": "...",
  "skill_versions": {},
  "model": "...",
  "model_profile": "...",
  "model_version_snapshot": "...",
  "temperature": 0,
  "seed": 0,
  "params_hash": "...",
  "prompt_hash": "...",
  "output_hash": "...",
  "metrics": {
    "p0": {},
    "p1": {},
    "p2": {},
    "p3": {}
  }
}
```

### 8.2 回归报告内容

| 项 | 说明 |
| ---- | ---- |
| 新增错误 | baseline 无、现在有 → 必须解释或修复 |
| 已修复 | baseline 有、现在无 |
| 未变 | 保持 |
| P0 门禁 | 通过 / 失败 |

### 8.3 确定性与抖动规则（v0.2 新增）

LLM 是非确定性的，而 P0 要求 100% 门禁——两者直接冲突，若不加处理，回归必然抖动。**低温度不等于确定**，模型服务端 API 会静默更新版本，因此不能只记 `model` 名。现实的失败结局是团队「重跑到通过」，门禁信誉随之崩塌。

规则：

1. 所有 LLM 调用必须 `temperature = 0`，并**记录模型版本快照**（`model_version_snapshot`，服务端返回的版本串）；落盘由 **Adapter 层负责**；
2. **同一 `model_version_snapshot` 下，P0 必须 100% 通过**；
3. **模型版本变更时**：先跑 3 次，把三次之间不一致的项登记为该用例的 `known_issues`（类别：模型抖动）；抖动率作为 P2 指标单独统计，**不计入 P0 失败**；
4. **禁止「重跑到通过」**：任何重跑必须作为新的 run 落盘（新的 `run_id`），同一个 run 只接受**首次产物**；重跑次数与原因必须记录；
5. **建立基线时**必须记录 3 次运行，用它们确定抖动率基线。

这套规则的目的：让「不确定」被**测量和管理**，而不是被隐藏。

## 9. 前置任务 0：档案盘点

在 M7 建立基线之前必须完成，否则门禁阈值无法设定。

| 盘点项 | 目的 |
| ---- | ---- |
| gold 用例实际数量 | 决定门禁覆盖能力与样本代表性 |
| silver 用例数量 | 决定趋势监控覆盖面 |
| bronze 用例数量 | 决定结构 / 版式回归覆盖面 |
| 报告类型分布 | 决定第一阶段锁定哪一类报告 |
| 已知错误样本 | 构造 known_issues 与陷阱用例 |
| **gold 用例的 G3 人工推导成本核算** | **逐用例核算专家工作量**，让 M7 排期不建立在不存在的样本上 |

若 gold 数量不足以支撑结论，必须**如实记录为已知限制**，不允许用 silver / bronze 冒充 gold。

## 10. 陷阱用例构造要求

至少构造以下类型的陷阱用例，每个都必须有对应的 expected_issues：

| 陷阱 | 系统必须的行为 |
| ---- | ---- |
| 输入缺少必需事实 | 报 `missing`，不得补全 |
| 同一事实多来源冲突 | 报 `conflict`，不得静默择一 |
| 单位异常（mm 与 m 混用） | 报量纲 / 单位错误 |
| 数值超出限值 | 判定方向正确，不得判反 |
| 表中合计与分项不符 | 报表内不自洽 |
| Narrative 段落含未锚定数字 | 报锚定失败 |
| 结论未覆盖全部检测项 | 报覆盖度不足 |

## 11. 第一阶段不做

- 与历史报告的逐项版式一致性自动判定
- 复杂样式继承链的自动判定
- 全文语义相似度指标
- 自动修复循环的自动验收（修复建议仅记录）
- 多模型 A/B 的自动化调度（先手工换 profile 跑）
- 无人值守的评测集扩充
